# Agent module — technical specification

Spec for a new **Agent** module in SaiHarness. Written to be handed to a fresh
implementation session (any capable model). Read `CLAUDE.md` first — this spec
assumes its architecture, conventions and testing rules.

---

## 1. Purpose and security framing

SaiHarness already has `shell_run` (in `tools_server.py`, logic in `core/shell.py`):
the local model can run arbitrary PowerShell on **this** machine, with a
per-call confirmation dialog and no allow-list. This module extends exactly that
capability to **other machines the user owns**, over an authenticated, encrypted
channel.

This is remote administration of the user's own hosts, done on the user's
explicit instruction. The module does not weaken the existing trust model — it
*adds* security on top of a plain remote shell:

- mutual TLS (both ends authenticated), traffic encrypted end to end;
- one-time enrollment tokens, so a leaked installer cannot enroll a second host;
- a per-agent client certificate the user can revoke at any time;
- the same human-in-the-loop confirmation dialogs and central logging the local
  `shell_run` already uses.

All work stays inside the project folder
`C:\Users\alexm\Desktop\SaiHarness\SaiHarnessAgentic`. Follow the repo workflow:
after a finished change, show the diff and a proposed commit message; commit and
push only after the user confirms.

## 2. Terminology

- **Main harness** — the existing PySide6 desktop app. Holds the brain
  (`ChatStreamer`), the permission UI, the model connection, and now the agent
  registry + certificate authority.
- **Agent / mini-harness** — a thin executor process running on a remote host.
  It has **no model of its own**. It exposes local capabilities (shell, file
  read/list/search) as tools and does only what the main harness tells it.
- **Enrollment** — the one-time bootstrap in which a freshly installed agent
  proves a single-use token and receives its long-lived client certificate.

---

## 3. Chosen architecture (decisions and rationale)

### 3.1 Thin executor, single brain

The agent is a **thin executor**, not an autonomous agent. The main harness's
existing `ChatStreamer` loop is the only brain. A connected agent surfaces in the
tool catalog as a set of tools (`host_<name>.<tool>`); when the model calls one,
`ToolRouter` dispatches it over the channel to that host and returns the result.

Why thin and not a loop-on-host design:
- Reuses the entire existing brain, catalog, permission and logging stack with
  almost no duplication.
- The host needs no inference connection at all, so it has exactly **one** network
  peer — the main harness — which is a hard requirement here.
- One place to confirm and log every write/shell action (`ui/permission.py`,
  `core.diag`), which is exactly where arbitrary remote execution needs oversight.

This supersedes earlier "run the agent loop on the host" sketches from the design
chat; the loop stays in the main harness.

### 3.2 Host dials out; one peer only

The agent always makes the **outbound** connection to the main harness
(`wss://<main-host>:<port>`). The host opens no listening port (smaller attack
surface, works through NAT/firewall). The agent trusts and talks to the main
harness and nothing else (enforced by CA pinning + a single configured address).

## 4. Cryptography and enrollment

### 4.1 Main harness as a mini certificate authority

- On first use the main harness generates a long-lived CA key + cert, stored in
  `data/agent/ca_key.pem`, `data/agent/ca_cert.pem`. `data/` is already in
  `.gitignore`. The CA key is the single most sensitive secret — restrict ACL.
- The main harness's TLS server cert is signed by this CA.
- Crypto material is generated by code using the `cryptography` library — **never**
  by the model. "The main harness generates the installer" means the harness fills
  a template with PEM strings produced by `cryptography`; the model never invents
  keys, certs or tokens.

### 4.2 One-time installer and enrollment (CSR flow)

The installer is an **individual, single-use** PowerShell script generated per
agent. It carries only: the main harness address, the CA certificate (for
pinning), and a one-time enrollment token. It does **not** carry a long-lived key.

```
main: generate installer.ps1  (address + CA cert + one-time enrollment token)
host: run installer.ps1
   -> connect to main over TLS, pin the CA            (main authenticated to host)
   -> present the enrollment token
main: verify token (valid, unused, not expired)
   -> host generates its OWN key pair, sends a CSR
   -> main signs the CSR with the CA, returns the client cert
   -> token burned (status = used)
   -> host downloads the thin wrapper + minimal deps over the SAME pinned channel
host: start the wrapper; on every later reconnect authenticate with the client
      cert (NOT the token — the token is used exactly once in the agent's life)
```

Properties this gives:
- "One-time" is real: a leaked installer is useless after first enrollment.
- The agent's private key never crosses the network (only the CSR does); the main
  harness stores only the cert **fingerprint**, never the agent's private key.
- Reboot / wrapper restart => reconnect with the stored client cert, no re-enroll.

### 4.3 Ongoing channel

- TLS 1.3 only (encryption, integrity, anti-replay, forward secrecy via ECDHE).
- mTLS: the agent presents its client cert; the main harness verifies it was
  signed by the CA, the fingerprint is in the agent registry, and status is active.
- The agent pins the CA (ignores the system trust store), so it will not talk to
  any other server even one with a valid public cert.

### 4.4 Downloading the wrapper

The wrapper code and deps are fetched over the already-pinned TLS channel, never
plain HTTP. Code from the main harness is trusted exactly as much as the main
harness (which the pinned CA authenticated).

## 5. Module layout (`core/agent/`, no Qt)

Keep crypto/network/logic free of Qt, like `core/shell.py`, `core/files.py`,
`core/memory.py`. Qt lives only in `ui/` and wiring in `worker.py` /
`ui/main_window.py`.

```
core/agent/
  ca.py          # CA generation, CSR signing, cert/fingerprint helpers (cryptography)
  enroll.py      # enrollment tokens (issue/verify/burn), CSR handling
  registry.py    # agent records: id, name, fingerprint, os, created_at,
                 #   expires_at, status(active/revoked/used); DB-backed
  protocol.py    # frame format + (de)serialization, correlation ids (no I/O)
  bridge.py      # IN-PROCESS: TLS listener, live socket per agent, dispatch,
                 #   contributes dynamic tools to the catalog
  wrapper.py     # the thin executor that runs on the host (reuses shell/files logic)
  templates/
    installer.ps1.tmpl   # per-agent installer template
```

### 5.1 Why the bridge is in-process (not a stdio MCP server)

Existing MCP servers are stdio subprocesses listed in `data/mcp.json`
(`core/mcp_manager.py`). The agent bridge is **different**: it holds live network
state (one open socket per connected host) and must drive the GUI permission
dialogs. So it lives in-process in the main app (near `worker` / the Qt app),
owning the agent-facing TLS listener and the live registry. It still *presents*
tools into the existing catalog, but it is not a stdio child.

### 5.2 Catalog / router integration

- The bridge contributes **dynamic** tool entries, one group per connected host,
  named `host_<name>.<tool>` (e.g. `host_alpha.shell_run`, `host_alpha.fs_read`).
- The catalog and `ToolRouter` are rebuilt per reply already (router created every
  message), so a dynamic roster that changes as agents connect/disconnect is cheap
  — just reflect the currently connected agents.
- On dispatch: if the tool name is `host_<name>.<real>`, route the call over that
  host's socket and await the result (match by correlation id); otherwise fall
  through to normal local handling.
- Tool descriptions must state the host name, OS and available roots, and that the
  action runs on a remote machine and is real/irreversible — so `describe_tool`
  is informative and the model does not target the wrong host.

### 5.3 Permissions

Reuse the existing model unchanged:
- Read-only remote tools (`host_*.fs_read`, `fs_list`, `fs_search`) run without
  asking.
- Write / shell remote tools (`host_*.shell_run`, `fs_replace`, `notes_write`)
  show the existing `ui/permission.py` dialog (File / Was / Will be), honour the
  "Auto-approve all confirmations" setting, and are logged via `core.diag`.
- The permission decision happens on the **main harness, before** the call is sent
  to the host. The host just executes what it is told; it does not re-implement
  the confirmation logic.

## 6. Channel frame format (over WebSocket)

One multiplexed `wss` channel per agent. All frames are JSON with a type and a
correlation id. Minimal set:

- `hello`        host -> main : { agent_id, proto_version }
- `capabilities` host -> main : { os, roots: [...], tools: [...] }   (on connect)
- `tool_call`    main -> host : { id, tool, args }
- `tool_result`  host -> main : { id, output, is_error }
- `ping`/`pong`  keepalive, either direction

Enrollment frames (`enroll_request`, `csr`, `cert_issue`) may share the transport
or use a dedicated short-lived endpoint — implementer's choice; keep them distinct
from the steady-state frames above.

Tool errors on the host follow the repo convention: the host returns
`ERROR_PREFIX + text` / sets `is_error`; reuse `core/markers.py` so a file whose
content starts with "ERROR" is not mistaken for an error (see CLAUDE.md "Tool
errors"). Honour `ToolRouter` repeat-error handling (`REPEAT_ERROR_BLOCK`,
`STUCK_NUDGE`) the same way as local tools.

## 7. The thin wrapper on the host

- Reuses the existing logic: `core/shell.py` for `shell_run`, `core/files.py` for
  `fs_read/list/search`. Vendor or download these so behaviour matches the local
  tools exactly (encodings: cp1251 fallback, CRLF/encoding preservation — keep
  as-is).
- Minimal deps only: `cryptography` (client cert + CSR, TLS context) and a
  WebSocket client (`websockets`). Bootstrapped the way `Run.cmd` /
  `scripts/bootstrap.py` do it: find Python, make a small venv, install pinned
  deps, run the wrapper.
- No model, no inference connection, no second peer.
- Decide and document: run once vs. install as a persistent background
  process/scheduled task so the agent reconnects after reboot (recommended:
  persistent, reconnecting with the stored client cert).

## 8. UI — the "Agent" area

A new right-hand tab (or a dedicated window like Connection / Model Builder) in
`ui/`, wired in `ui/main_window.py`:

- **Create agent**: name it -> main generates the one-time `installer.ps1` and
  shows it / saves it for the user to run on the target host.
- **Agent list**: name, OS, fingerprint (short), status, connected/disconnected.
- **Revoke**: flip registry status to `revoked`; the bridge drops the socket and
  refuses future connections with that cert.
- Follow `ui/themes.py` (take colours from `themes.current()`, not constants) and
  rebuild on `themes.bus.changed` like the other panels.

## 9. Model context

The model must understand: these tools execute on a remote machine; there can be
several distinct hosts; actions are real and irreversible. Do this **without**
bloating the system prompt, mirroring `core/memory.py`:

- Add `agents.prompt_block` (called where `MainWindow._tools_text` builds the
  catalog, like `memory.prompt_block`) that appends e.g.
  `Connected hosts: alpha (Windows), beta (Linux)` **only when** at least one
  agent is connected. Empty otherwise, so the prompt does not grow when there are
  no agents.
- A short standing line in the system prompt: "You have agents on remote hosts;
  calling their tools runs commands on that machine." Keep the compact style of
  the existing catalog.

## 11. Phased implementation plan

Do **not** build everything at once. Suggested phases, each independently
testable:

0. **Skeleton + deps + CA.** Add deps; create `core/agent/` skeleton; implement
   `ca.py` (CA gen, CSR sign, fingerprints) with an offline test.
1. **Enrollment.** `enroll.py` + `registry.py` + DB table; token issue/verify/burn;
   CSR -> signed cert. Test over loopback, no UI yet.
2. **Channel.** `protocol.py` + `bridge.py` listener + `wrapper.py`; one agent
   connects over TLS (mTLS, CA pinning) on 127.0.0.1 and the main lists it.
3. **Catalog + dispatch + permissions.** Surface `host_<name>.<tool>`; route via
   `ToolRouter`; wire read-only vs write to `ui/permission.py`.
4. **UI "Agent" tab.** Create (generate installer), list, revoke, status.
5. **Context block.** `agents.prompt_block` + system-prompt line.
6. **Polish.** Persistence/reconnect on the host, docs (`TEST_PLAN.md` additions),
   finalize tests in `tests/run_all.ps1`.

## 12. Testing (follow repo conventions, see CLAUDE.md)

- Each test is a standalone `tests/test_*.py` printing `OK`/`FAIL` lines and
  `ALL OK`; take the temp DB path as `argv[1]`; set `db.DB_PATH` to it; never touch
  `data\saiharness.db`. Add every new test file to `tests/run_all.ps1` (lists are
  hardcoded there).
- Use `ROOT = Path(__file__).resolve().parents[1]` for project paths; never a
  hardcoded copy.
- Crypto tests run offline. Channel/enrollment tests use loopback (127.0.0.1) with
  a generated throwaway CA; no real remote host. Gate any local-network behaviour
  behind an env flag the way the web module uses `SAI_WEB_ALLOW_PRIVATE`.
- Keep everything English per CLAUDE.md (UI, prompts, tool descriptions, comments,
  tests, docs). Reuse `core/markers.py` for error/`NOT_FOUND` strings; do not add
  new Russian strings.

## 13. Open decisions for the implementer

1. Host wrapper: run-once vs. persistent service/scheduled task (recommend
   persistent, reconnecting with the client cert).
2. Client-cert lifetime (e.g. 90 days -> regenerate the agent) vs. long-lived with
   revocation only.
3. Whether enrollment frames share the steady-state channel or use a dedicated
   short-lived enrollment endpoint.
4. Exact tool naming/grouping in the catalog (`host_<name>.<tool>` vs. a meta-tool
   `agent` param mirroring the existing `call_tool(tool=...)` style).
